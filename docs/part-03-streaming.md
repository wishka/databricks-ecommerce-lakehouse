# Part 3 — Structured Streaming

**Время:** 2–3 часа. **Результат:** `gold.sessions_5min` обновляется near-real-time
и досчитывается без дублей после рестарта.

## Как запускать

Два ноутбука работают одновременно:

1. `03_streaming/30_clickstream_producer.py` — подкладывает файлы событий
   в `landing/clickstream_live/` (например, 30 батчей по 500 событий каждые 20 секунд).
2. `03_streaming/31_streaming_aggregations.py` — читает Auto Loader'ом,
   считает 5-минутные окна, апсертит в Delta.

Удобно: продюсер — в одной вкладке браузера, консьюмер — в другой.
Или обе задачи в джобе `ecom_streaming` (они без `depends_on`, значит параллельны).

## Четыре вещи, которые надо понимать

### 1. Event time против processing time

Агрегируем по времени события (`event_ts`), а не по времени прихода файла.
Иначе сеть моргнула на 10 минут — и весь всплеск «переехал» в другое окно.

### 2. Watermark

```python
.withWatermark("event_ts", "15 minutes")
```

Это обещание движку: «событий старше 15 минут от максимума мы больше не ждём».
Оно позволяет:

* закрывать окна и отдавать результат в режиме `append`;
* ограничивать состояние — без watermark оконная агрегация копит его вечно;
* ограничивать состояние дедупа (`dropDuplicatesWithinWatermark`).

Цена: события, опоздавшие сильнее, отбрасываются. Смотрите
`numRowsDroppedByWatermark` в `lastProgress` — если растёт, окно мало́.

Генератор специально шлёт 10% событий с опозданием 5–20 минут: часть попадёт
в окно, часть будет отброшена. Это видно в метриках.

### 3. Чекпоинт — это состояние запроса

Удалили чекпоинт → стрим перечитает всё заново. Поменяли схему агрегата или
набор ключей группировки → старый чекпоинт несовместим, нужен новый путь.
Чекпоинты здесь лежат в `landing/_checkpoints/<stream>` — служебной ветке volume.

### 4. `foreachBatch` вместо прямой записи

Delta-таблица не умеет принимать `outputMode("update")` напрямую.
`foreachBatch` даёт обычный батчевый DataFrame — с ним можно MERGE,
запись в несколько мест, вызов внешнего API:

```python
def upsert_window(batch_df, batch_id):
    batch_df.createOrReplaceTempView("window_updates")
    spark.sql("MERGE INTO gold.sessions_5min AS t USING window_updates AS s ...")
```

`batch_id` в сигнатуре — для идемпотентности: при рестарте батч может прийти
повторно, MERGE по ключу окна перезапишет его теми же значениями.

## Stream-static join

Статическая сторона (`silver.products`) перечитывается на каждом микробатче,
значит изменения справочника подхватываются автоматически. Обратное неверно:
уже записанные строки не пересчитываются. Если вам нужна «переписанная история»
при изменении справочника — это батч-пересчёт, а не стрим.

## Проверка идемпотентности

1. Запустите консьюмер в режиме `available_now`, дождитесь завершения.
2. Запишите `SELECT count(*), sum(events_cnt) FROM gold.sessions_5min`.
3. Запустите продюсер ещё раз, потом консьюмер.
4. Числа должны вырасти ровно на новые события — без дублей.

## Мониторинг

```python
for q in spark.streams.active:
    p = q.lastProgress
    print(p["numInputRows"], p["durationMs"], p["stateOperators"])
```

В проде — `StreamingQueryListener`, пишущий метрики в таблицу; пример в ноутбуке.

## Частые проблемы

**Стрим стартует и сразу завершается, таблица пуста** — продюсер ещё не записал
файлы, или путь не совпадает. Проверьте `landing/clickstream_live`.

**`Query ... terminated with exception: ... schema mismatch`** — поменялась схема
источника, а чекпоинт старый. Удалите чекпоинт и `schemaLocation` этого стрима.

**Состояние растёт, задача съедает квоту** — забыли watermark либо
группируетесь по ключу с неограниченной кардинальностью (например, по `event_id`).

**В Free Edition стрим долго стартует** — serverless поднимается по требованию;
для демо используйте `availableNow`, а не `processingTime`.
